# Порядок выполнения и проверки

## 0. Подготовка
- Работайте только на своей лабораторной копии WordPress.
- Сделайте резервные копии файлов и базы данных.
- Уточните тип веб-сервера: Apache/LiteSpeed или Nginx.
- Не публикуйте секреты из wp-config.php.

## 1.1 Очистка корня — 10 баллов
Проверьте web-root на readme.html, license.txt и забытые резервные копии (*.sql, *.zip, *.bak). Удаляйте только подтверждённые ненужные файлы после резервного копирования. Сохраните снимок каталога после очистки.

## 1.2 Права CHMOD — 10 баллов
Эталон из методички: каталоги 755, обычные файлы 644, wp-config.php 400 или 440. Пример для Linux (проверьте путь и владельца до запуска):
```bash
find /path/to/wordpress -type d -exec chmod 755 {} \;
find /path/to/wordpress -type f -exec chmod 644 {} \;
chmod 440 /path/to/wordpress/wp-config.php
stat -c '%a %U:%G %n' /path/to/wordpress/wp-config.php
```
Выполняйте с учётом модели PHP-FPM/владельца. Если PHP не может прочитать wp-config.php после 400/440, исправьте владельца/группу корректно, не открывая файл всем.

## 1.3 Защита wp-config.php — 10 баллов
Скопируйте корневой .htaccess из проекта в web-root. На Apache 2.4 запрос /wp-config.php должен вернуть 403 (или 404, если сервер скрывает существование файла), не содержимое. Проверка:
```bash
curl -i https://example.test/wp-config.php
```

## 2.1 Запрет PHP в uploads — 15 баллов
Скопируйте uploads/.htaccess в wp-content/uploads/. В тестовой среде временно создайте test.php с безопасным содержимым:
```php
<?php echo 'OK'; ?>
```
Откройте /wp-content/uploads/test.php. Ожидаемый результат — 403. Немедленно удалите test.php. Не оставляйте тестовый PHP-файл в публичном каталоге.

## 2.2 Отключение редактора — 10 баллов
Добавьте в wp-config.php выше строки “That's all, stop editing!”:
```php
define('DISALLOW_FILE_EDIT', true);
```
Войдите в wp-admin и подтвердите отсутствие встроенных редакторов тем и плагинов. Эта константа отключает редактор кода, но не заменяет обновления и контроль доступа.

## 2.3 Безопасное логирование — 10 баллов
В лабораторной среде используйте WP_DEBUG=true, WP_DEBUG_DISPLAY=false, WP_DEBUG_LOG=true. Убедитесь, что ошибки не выводятся посетителям. Защитите debug.log от HTTP-доступа и ограничьте права на журнал. После сдачи отключите отладку на production.

## 3.1 Перенос wp-config.php — 15 баллов
WordPress умеет искать wp-config.php на один уровень выше каталога установки. Сначала сделайте резервную копию. Переместите файл из document root в родительский каталог, проверьте владельца/права и загрузку сайта. Не перемещайте его в публичную папку другого виртуального хоста. Сохраните снимок структуры каталогов и работающей главной страницы.

## 3.2 Префикс таблиц — 10 баллов
Зафиксируйте фактическое значение $table_prefix из своего wp-config.php. Стандартный wp_ упрощает угадывание имён таблиц при уже существующей уязвимости или утечке схемы. Уникальный префикс снижает предсказуемость имён, но НЕ защищает от SQL-инъекции. Для существующей установки изменение префикса требует миграции таблиц, options/usermeta и проверки сериализованных данных. Не меняйте его простой заменой строки.

## Nginx (если Apache .htaccess не работает)
Добавьте в соответствующий server/location context и проверьте конфигурацию перед reload:
```nginx
location = /wp-config.php { deny all; }
location ~* ^/wp-content/uploads/.*\.(php[0-9]?|phtml|phar|phps)$ { deny all; }
location ~* /\.(?!well-known/) { deny all; }
```
Разместите правила в корректном контексте конфигурации; .htaccess на Nginx не читается.

## Аудит
```bash
php tools/audit.php /path/to/wordpress
```
Скрипт только читает состояние и выводит предупреждения. Он не меняет права и не удаляет файлы.

## Доказательства к отчёту
1. Корень после очистки.
2. CHMOD wp-config.php.
3. HTTP 403/404 для /wp-config.php.
4. uploads/.htaccess и HTTP 403 тестового PHP.
5. wp-admin без редакторов.
6. Фрагмент wp-config.php без секретов.
7. Дерево каталогов после переноса и работающая главная.
8. Строка $table_prefix (без иных секретов).
